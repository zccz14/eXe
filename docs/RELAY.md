# 中继的下行传输：为什么是 SSE + D1 轮询

一页决策记录。改传输形态之前先读这里，别从头再讨论一遍。

## 决策

设备下行保持 **SSE（HTTP 长连接）**，队列与状态放 **D1**，Workers 在 1 秒的轮询节拍里取件。
**不引入 Durable Object，也不引入 WebSocket。**

## 为什么不是 WebSocket + Durable Object

三件事被混在一起，先拆开：

1. **回传**（`received` / `result`）是普通 HTTP POST，任何方案都一样。
2. **下行**可以是 SSE，也可以是 WebSocket。
3. **队列**可以放 D1，也可以放 DO。

其中唯一强绑定是：**Hibernation 只认 WebSocket Hibernation API**。SSE 没有任何休眠机制，
DO 举着一条 SSE 流就一直按 128 MB 计时长。所以「DO + SSE」是一个陷阱：
时长账单照付，却拿不到即时推送（Worker 无法把 DO 的事件推进一条已打开的 SSE 响应），
仍然要轮询。

而「WS + DO Hibernation」也不省：**额度单位的价格差 150 倍**。

| | 包含额度（Paid） | 超量单价 | 每次调用的成本 |
|---|---|---|---|
| D1 行读 | 250 亿 / 月 | $1 / 十亿行 | 空转读几行 |
| DO 请求 | 100 万 / 月 | $150 / 十亿请求 | **~1.1 个请求**（`stub.fetch` 唤醒 + 消息按 20:1） |

DO 的 100 万请求额度，在「每天 100 次调用/台」下只够约 **300 台**；
而 D1 的 250 亿行额度在同样估算下够 **数千台**。延迟从 1 秒变成即时，
换来的是容量掉一个数量级——在「1 秒以内的延迟不值得为它付钱」的前提下，这笔交易不成立。

## 容量估算

假设：空转时每秒 1 次只读 peek（3 个 EXISTS 子查询，约 3 行读），有活才写。

| 维度 | 现状能撑 |
|---|---|
| D1 行读（Free 500 万/天） | ≈ 20 台常连设备 |
| D1 行读（Paid 250 亿/月） | ≈ 3,000–5,000 台常连设备 |
| D1 写 | 空转 0 写；每次调用 2–3 条（claim、result、touch） |
| 单连接时长 | 900 秒后由 agent 重连（`STREAM_MAX_SECONDS`） |

真正的天花板不是配额，是**同一时刻的 SSE 连接数**与单库读吞吐——这两个没有官方数字，
要到量之后实测。上表是量级估算，不是承诺。

## 已经做掉的优化

- **空转只读**：`peek()` 用一条 `SELECT ... EXISTS(...) x3` 同时判断「有无待投递 / 有无待重投 / 有无待取消」，
  只有为真才执行 `UPDATE ... RETURNING` 的抢占语句。空闲设备不再每秒产生写语句，
  不会争用 D1 的单主库。
- **写只发生在真事件上**：`claimCall` / `claimReplays` / `claimCancellation` 全部由 peek 门控。
- **低频维护**：`touchAgent`（在线状态）与 `sweep`（过期标记）每 30 秒一次。
- **重投**：每 15 秒检查一次超过 120 秒未结算的调用，重发同一 `call_id`；设备侧按 `call_id` 幂等。

## 硬规则

1. **不要在 DO 里举着 SSE**：拿不到 Hibernation，等于按 128 MB 包月。
2. **不要在 DO 里轮询或 `setTimeout`**：pending timer 阻止休眠，账单和轮询一样。
3. 如果哪天真上 WS：只用 **Hibernation API**（`state.acceptWebSocket`），心跳走
   `setWebSocketAutoResponse`，过期靠懒判断而不是周期性 alarm，每个设备一个 DO。
4. 传输形态变了，**协议不变**：信封、签名、`call_id` 幂等都在协议层，换传输不动 `docs/PROTOCOL.md`。

## 什么时候重议

任一出现就重新打开这份记录：

- 1 秒的取件延迟开始影响产品（例如需要交互式流式输出）；
- 同时在线设备到几十上百台，D1 读延迟或连接数开始抖（届时先调大轮询间隔，再考虑 DO）；
- 需要**跨设备协调**（同一个控制台地址的多台设备抢占同一任务、广播），那是 DO 的强项，不是传输的问题。

## 可调的旋钮

| 旋钮 | 现在 | 作用 |
|---|---|---|
| 轮询间隔（`sleep(1000)`） | 1 s | 线性换取容量与延迟 |
| 控制台轮询间隔 | 2–5 s | 控制台每次轮询都是自签请求，会写一条 `request_nonces`；写量上来先调大它 |
| `STREAM_MAX_SECONDS` | 900 s | 单连接寿命，决定重连频率 |
| `LOST_AFTER_SECONDS` | 120 s | 多久没结算就重投 |
| `sweep` / `touchAgent` 周期 | 30 s | 维护写频率 |
