# eXe 威胁模型

## 参与方

| 角色 | 持有 | 能做什么 | 不能做什么 |
|---|---|---|---|
| 人 | 设备的信任列表 | 在控制台填设备地址、在设备上填控制台地址 | — |
| 控制台（浏览器） | **唯一一份控制台私钥**、自己浏览器里的一份设备名单 | 记住/忘掉设备、签发调用、解封结果 | 直接命令设备以外的机器 |
| 云端（CF Worker + D1） | 地址（公钥）、两个方向的信封、签名、状态（两张表：`devices`、`calls`） | 排队、路由、限流、转发 | 签名、解密、伪造或改写内容；知道调用了什么工具、参数是什么、结果是什么 |
| 设备（eXe agent） | 设备私钥、信任列表 | 验签、执行、封装结果、自签每次请求 | 执行来源不在信任列表里的调用 |
| 陌生人 | 一对自生成的钥匙 | 向任意地址排队，占用队列与设备的注意力（见「谁能对一台设备拒绝服务」） | 让设备执行、解密、冒充任何一方 |

密钥只有一把：Ed25519 既签名又派生 X25519（`edwardsToMontgomery(pub)` / `clamp(sha512(seed)[0..32])`），
没有第二份材料需要保管、传输或托管。

## 建立的信任

- 设备信任**一个**东西：配置里的 `trust` 地址列表。它由人写在设备上，云端既看不到内容也改不了它；签名验不过就丢弃。
- 云端信任每一方的方式都一样：每一次请求都由该地址自签（method、path、address、时间戳），
  **没有 bearer 令牌，也没有登录**——控制台和设备的鉴权是同一条代码路径。
  云端不记请求、不去重：安全来自「每个效果都由发送者签过的 `call_id` 定死」，不来自一张用过的号码表。
- 结果机密性：设备把正文封给签发者的 X25519 公钥（同一把密钥派生），
  曲线运算只裹 32 字节内容密钥，正文用 AES-256-GCM；落库只有信封。

## 防线与它的诚实边界

| 攻击 | 结果 |
|---|---|
| 截获一条设备请求（日志、代理） | 300 秒内可以原样重发，但重发只重复幂等动作：建单撞 `call_id` 主键、回执重写同一时间戳、结果封逐字节比对（同封 204 / 异封 409）。它不含任何签名能力，重放不出第二种效果 |
| 中间人改调用内容 | 签名覆盖 `call_id/issuer/device/issued_at/expires_at` 与 `sealed` 的原始字节，改一个字节即失效 |
| 重放旧调用 | 有效期随报文一起签名，过期即丢弃；有效期内重投由设备侧内存幂等接住，不重复执行 |
| 冒名投递 | 调用必须由发起请求的那个地址签发（`issuer == 请求签名的地址`），换个 `x-exe-address` 就验不过签名。中继不按任何名单过滤——它从来不是边界；真正拒绝发生在设备的 `trust` 上 |
| 云端数据库被拖库 | 只有地址、调用/结果**信封**与签名。没有任何一把钥匙能解开历史结果 |
| 云端进程被完全攻破 | 攻击者能丢包、延迟、拒绝、重放（重放受时间窗与幂等键约束，见下节），但**签不出调用、解不开指令、解不开结果**。它也无法让设备信任任何新身份——信任只在设备配置里 |
| 浏览器被攻破 | 这是新的信任根，而且没有账号层可以撤销。XSS 能借你的钥匙签名与解密。私钥被包在不可导出的 AES-GCM 密钥下，只提高取走难度，不改变"同源即等同密钥"这个事实 |
| 设备丢失 | 撤销是把它的地址从设备 `trust` 里删掉并重启；控制台里「忘掉」只是这个浏览器不再列出它，不授权也不撤销。设备本地仍持有历史明文缓存（若有），撤销不等于擦除设备 |
| 云端冒充签发者 | 做不到：设备只认配置里那些地址，签名验不过就丢弃 |

## 谁能对一台设备拒绝服务

三档，按「攻击者需要什么」排：

| 谁 | 需要什么 | 能造成什么 |
|---|---|---|
| 云端被完全攻破 | 拿下 worker 或 D1 | 丢包、延迟、丢掉回执、不记录。设备无法区分「没人调用我」和「云端不给我」——这是架构代价，不是待修缺陷 |
| 任何陌生人 | 一对自生成的钥匙。设备地址不可枚举，但泄露一次（`trust` 配置、日志、截图）就等同公开 | 排队不需要任何关系，见下 |
| 控制台被攻破 | 你的浏览器 | 以你的名义签发调用——那时已经不是 DoS |

陌生人不需要任何关系就能 `POST /api/devices/{address}/calls`：中继只检查信封是不是由请求者自己签的。三条路径：

1. **队头堵死。** 下行窗口取「最旧的 N 封」且按 `created_at` 排序，而「发过没有」只活在那条连接的内存里——`queued` 行不会因为被发过而让位。于是几十 KB 的垃圾调用就能把真调用挤到窗口外，直到垃圾自己的 `expires_at` 到期（上限 1 小时）。这期间控制台显示 `queued`、设备显示在线、什么都不发生，比离线更难诊断。
2. **存量放大。** `calls` 只增不减（没有删除路径），Paid 单库 10 GB，一次插入写 4 行（表 + 3 个索引）。没有在队上限时，攒存储对攻击者比付账单对我们更便宜：约 10 万封 96 KiB 的调用就能把库填满，然后**全站**不可用。
3. **设备侧算力。** 每个被推送的陌生信封都要过一次验签。若实现顺序是「先验签、再查 `trust`」，陌生人的 96 KiB 密文会先跑完整的 transcript 哈希（O(密文大小)）；反过来只需一次字符串比较。

**中继只能限量，不能按身份拦**——理由见「关于社交图」那一节。可用的旋钮：每设备在队上限 + 条件插入（超了 429）、推送窗口轮转（配合上限把饥饿压到 ⌈上限/窗口⌉ 拍）、每连接推送预算（字节/秒）、以及设备侧先比 `trust` 再验签。

边界要说清：**上限管住存量，管不住流量。** 用很短的 TTL 反复冲刷仍能把 D1 的写配额当燃料烧；挡这个需要工作量证明、付费或容量告警后人工处置，属于另一类决定，当前没有做。

## 关于社交图：一句诚实的更正

**云端已经能重建社交图的「已使用子集」。** 每条 `calls` 行就是一条 `(issuer, device)` 边，还带时间、频次和密文长度；聚合一下就是谁在指挥谁。所以「不上传 `trust` 列表是为了保护社交图」这个理由是错的——已经被用过的边早就写在库里了，而且比一份名单更细。

不上传 `trust` 的真实理由与保密无关，只有两个：

1. **不把准入权交给云端。** 如果云端按 `trust` 过滤，「签名合法就执行」就变成两处实现，必然漂移，最后没人再相信设备那一道。云端不知道名单，也能完成它该做的全部事情。
2. **快照不能当授权。** 上传的名单必然过期；拿一份陈旧的白名单做准入决策，就是把过期数据当权威。

想让图真的收窄，只有让**每条边对外不可连接**：控制台为每台设备算 `tag = HMAC(控制台私钥, "edge" ‖ device)`，库里存 `tag` 而不是 `issuer`，并把真实 `issuer` 封给设备（设备要它来验签）。云端于是只能看到「某个匿名控制台 ↔ 这台设备」，看不到「同一个控制台 ↔ 十台设备」。

它不便宜，代价至少三条：中继再也验不了调用签名（`T_call` 覆盖 `issuer`，没它就没法验）；每次投递多一次密封；`GET /api/calls` 要改成按客户端提交的 tag 查。**这是真选项，不是免费的隐私开关，尚未实现。**

## 托管等级

只有一档：**`device`**。密钥只存在于端侧（浏览器 / agent 进程）；云端不持有任何可签名、可解密的材料，只做盲中继。

云端能看到的全部字段：

```
call_id, issuer(签发者地址), device(设备地址), sealed, sig, issued_at, expires_at, 状态
```

看不到：工具名、参数、输出、结果正文。

**代价**：

- 没有装过钥匙的浏览器读不到历史结果，也签不出调用；换浏览器、清缓存都会遇到。
  换一个浏览器就是换一个身份，没有别的说法。
- 云端无法做任何"内容相关的判断"（比如"禁止 rm -rf"），因为它看不见内容；设备侧也没有第二道许可——**信任列表是唯一闸门**。
- **没有本地策略（刻意取舍）。** 当前版本不提供 allow/deny：来自 `trust` 的调用会直接执行，包括 shell（以设备用户身份、无沙箱）。这把"信任错人"的后果放大成"整台机器"，所以只在你能对那台设备上的 `trust` 负责时才添加地址。
- **不做密钥恢复。** 丢钥匙就是换身份：浏览器清缓存/换设备会得到新地址，设备重装也会得到新地址；
  人重新在两个方向各填一次地址即可。这是刻意选择：一旦云端（或任何第三方）能替你找回钥匙，
  它也就握住了那把钥匙，下面「托管等级」这一档就不成立了。

## 云端被攻破时的确切边界

一句话：**泄露的只有设备目录和近期流量记录；没有任何私钥，也不存在"攻破云端就直接控制设备"的路径。**

| 会泄露 | 不会泄露 | 不会发生 |
|---|---|---|
| 已登记地址、在线状态、最近活跃时间、主机名/平台/版本 | 任何私钥（端侧生成，从未上传） | 攻击者伪造指令（签不出） |
| 调用元数据：`call_id`、issuer/device 地址、密文长度、时间、状态 | 指令内容、参数、执行输出 | 攻击者解密任何一条密文 |
| 设备名册（`devices`：地址、主机名、平台、版本、最后活跃） | 任何控制台的设备名单（它在浏览器里） | 攻击者把某台设备从任何人的名单里删掉 |
| **调用图**：每条 `calls` 行就是一条 (issuer, device) 边，带时间与频次 | 从未使用过的 `trust` 条目 | 攻击者凭空造出一条边（每条边都得有一封真签名的调用） |
| 传输层日志（时间、字节数、状态码） | 设备信任列表 | 攻击者让设备信任新身份（trust 在设备配置里） |

要让这句话**字面成立**，还有两件事必须做，都不是密码学问题：

1. **重放**：攻击者拿到一条仍在有效期内的旧请求或旧调用，可以原样重投。这条路
   已经被**幂等键**堵住，而不是被一张 nonce 表堵住：`call_id` 由发送者签发并被签名覆盖，
   服务端从不自己生成 ID，于是重投建单撞主键、重投回执重写同一个时间戳、
   重投结果封逐字节比对（同封 204 / 异封 409）。这条是**不变量**：任何新增的写入路径
   都必须满足「幂等键由请求者签发、被签名覆盖」，否则重放会立刻变质（追加型写入——
   计数、流水、清空历史——是最容易被忽略的一类）。
   除此之外还有两层：有效期随报文一起签名（`expires_at` 在签名范围内，过期即丢弃），
   以及设备侧内存幂等——进程内保留 `call_id → 结果`，同一个 `call_id` 再次到达时
   **不重复执行**，直接回已产出的结果；进程重启后映射消失，这正是想要的边界。

   **残留**（删掉 nonce 表换来的一点点代价，明确承认）：
   - 拿到 `GET /v1/devices/{address}/stream` 的一条仍在 300 秒内的请求，可以以该设备身份
     再开一条流：能收到发往该设备的信封（**解不开**），并让真设备最多晚 120 秒拿到。
     内容零泄露，最坏结果是一次重复投递。
   - 重放设备那条 `received` 回执，能让控制台显示一个并不存在的「已收到」。
     它不阻挡结果提交（`queued` 也接受结果），也不阻挡过期。
   - 云端的元数据（谁在什么时候给哪台设备发了多少字节）本来就可被中继看到；
     重放不增加新的元数据，只是重复一次同样的可见性。

2. **控制台来源完整性（部分缓解）**：设备不会被直接控制，但你**登录被攻破的 exe.ntnl.io 时**，
   攻击者的 JS 可以用你浏览器里的私钥签名。控制台现在是 Pages 上的纯静态资源，与中继
   解耦（`VITE_API_BASE` + CORS），但静态资源本身的完整性仍依赖 Pages 的发布流程；
   在拆 origin 完全落地之前，先接受这个风险。

## 谁能拒绝服务

云端的权力没有消失，只是变小了：它可以不投递、投递延迟、丢掉回执、不记录你的设备。
它不能做的事写在上面那张表里。

## 谁在签发

调用由**端侧身份**签发：现在是控制台自己那把密钥，它的地址就是它的全部身份。Agent（跑在任意地方的控制器）同样是一把 Ed25519 身份；
它驱动哪些设备，写在设备的 `trust` 配置里，云端只能存、不能改。

## 不做的事

- 不把任何长期令牌当作执行授权。
- 不在 D1/R2/日志里保留结果明文。
- 不用「服务端签名」代替「人签名」：云端可以有自己的运维签名，但那不赋予执行权。
- 不引入账号体系：一旦云端认人（`user_id`、JWT、登录会话），归属就不再由签名回答，
  密钥也就不再是身份。
