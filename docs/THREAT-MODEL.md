# eXe 威胁模型

## 参与方

| 角色 | 持有 | 能做什么 | 不能做什么 |
|---|---|---|---|
| 人 | AuthMini 账号、设备上的本地策略 | 批准/撤销设备、改策略 | — |
| 控制台（浏览器） | AuthMini 会话 JWT | 创建设备调用、读结果 | 直接命令设备以外的机器 |
| 云端（CF Worker + D1） | 账号**公钥**、调用签名、结果信封、设备令牌哈希 | 排队、路由、限流、转发 | 签名、解密、伪造或改写调用；在存储里保留结果明文 |
| 设备（eXe agent） | 设备签名私钥、设备 KEX 私钥、本地策略 | 验签、执行、封装结果 | 被云端"说服"绕过策略 |

## 建立的信任

- 设备信任**一个**东西：`account.sig_pub`，由人在配对时批准，写入本地配置，此后只认它。
- 云端信任设备的方式：设备用 `device.sig_pub` 签每一次回传；令牌只是"能连上来"的凭证，不是执行授权。
- 结果机密性：设备用 `X25519(device_eph_sk, account.kex_pub)` 派生一次性密钥封装，落库只有信封。

## 防线与它的诚实边界

| 攻击 | 结果 |
|---|---|
| 拿到设备令牌的人（令牌泄露 / 日志泄露） | 能连 SSE、能 ack，但**发不出可执行的调用**——调用必须带账号签名，而令牌不含签名能力 |
| 中间人改调用内容 | 签名覆盖 `call_id/device_id/account_id/name/args_hash/iat/exp/nonce`，改一个字节即失效 |
| 重放旧调用 | `nonce` + 单次状态机（queued→delivered→received→settled），终态之后一律 409 |
| 跨租户投递 | 签名里带 `account_id`，与设备登记的 owner 不符直接拒绝 |
| 云端数据库被拖库 | 只有公钥、调用签名与结果**信封**。没有任何一把钥匙能解开历史结果 |
| 云端进程被完全攻破 | 攻击者能丢包、延迟、拒绝、重放（都会被设备的 nonce/有效期挡住），但**签不出调用、解不开结果**。唯一残余风险：在你正登录时用它自己的公钥重新登记账号并诱你批准新设备——所以批准页必须比对 SAS，且设备端会拒绝对不上的人 |
| 浏览器被攻破 | 这是新的信任根。XSS 能借你的钥匙签名与解密。私钥被包在不可导出的 AES-GCM 密钥下，只提高取走难度，不改变"同源即等同密钥"这个事实 |
| 设备丢失 | 控制台撤销 → 令牌立刻失效；但设备本地仍持有历史明文缓存（若有），撤销不等于擦除设备 |
| 伪装配对（云端换掉账号公钥） | 设备与控制台同时显示同一个 SAS（账号公钥 + 设备公钥的短指纹）。人比对不上就不批准 |

## 托管等级（custody tier）

| tier | 账号私钥在哪 | 结果谁能解密 | 状态 |
|---|---|---|---|
| `browser`（唯一实现） | 人的浏览器：IndexedDB 里由**不可导出**的 AES-GCM 密钥包裹 | 只有那个浏览器 | 已实现 |
| `delegated`（计划） | 浏览器把**一次性、限权、限时**的会话密钥授给某个 agent | 该会话 + 浏览器 | 计划中。给 Cybion 这类"服务端 agent 要读结果"的场景用，不是长期托管 |

代价要说清楚：换成 `browser` 之后，**没有装过钥匙的浏览器读不到历史结果，也签不出调用**。换设备、清缓存、换浏览器都会遇到这件事。导出恢复材料的流程是下一步要补的（用 passkey 派生密钥包裹后再存云端，云端仍解不开）。

## 谁能拒绝服务

云端的权力没有消失，只是变小了：它可以不投递、投递延迟、丢掉回执、在批准页显示错误的 SAS（人一比对就会发现）。它不能做的事写在上面那张表里。

## 不做的事

- 不把设备令牌当作执行授权。
- 不在 D1/R2/日志里保留结果明文。
- 不用「服务端签名」代替「账号签名」：云端可以有自己的运维签名，但那不赋予执行权。
