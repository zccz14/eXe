# eXe 威胁模型

## 参与方

| 角色 | 持有 | 能做什么 | 不能做什么 |
|---|---|---|---|
| 人 | AuthMini 账号、设备上的本地策略 | 在控制台填设备地址、在设备上填信任地址、改策略 | — |
| 控制台（浏览器） | AuthMini 会话 JWT + **唯一一份账号私钥** | 添加/移除设备、签发调用、解封结果 | 直接命令设备以外的机器 |
| 云端（CF Worker + D1） | 地址（公钥）、两个方向的信封、签名、一次性 nonce | 排队、路由、限流、转发 | 签名、解密、伪造或改写内容；知道调用了什么工具、参数是什么、结果是什么 |
| 设备（eXe agent） | 设备私钥、本地策略 | 验签、执行、封装结果、自签每次请求 | 被云端"说服"绕过策略 |

密钥只有一把：Ed25519 既签名又派生 X25519（`edwardsToMontgomery(pub)` / `clamp(sha512(seed)[0..32])`），
没有第二份材料需要保管、传输或托管。

## 建立的信任

- 设备信任**一个**东西：配置里的 `trust` 地址列表。它由人写在设备上，云端既看不到内容也改不了它；签名验不过就丢弃。
- 云端信任设备的方式：设备每次请求都用同一个地址自签（method、path、address、时间戳、一次性 nonce），云端验签并拒绝重放的 nonce。**没有 bearer 令牌**。
- 结果机密性：设备把正文封给签发者的 X25519 公钥（同一把密钥派生），
  曲线运算只裹 32 字节内容密钥，正文用 AES-256-GCM；落库只有信封。

## 防线与它的诚实边界

| 攻击 | 结果 |
|---|---|
| 截获一条设备请求（日志、代理） | 时间窗内也无法重放：`(address, nonce)` 已经在库里，第二次直接 401。它也不含任何签名能力 |
| 中间人改调用内容 | 签名覆盖 `call_id/issuer/device/issued_at/expires_at` 与 `sealed` 的原始字节，改一个字节即失效 |
| 重放旧调用 | 有效期随报文一起签名，过期即丢弃；有效期内重投由设备侧内存幂等接住，不重复执行 |
| 跨租户投递 | 调用必须由该账号登记的地址签发（`issuer == account.address`），且设备地址必须属于该账号 |
| 云端数据库被拖库 | 只有地址、调用/结果**信封**与签名。没有任何一把钥匙能解开历史结果 |
| 云端进程被完全攻破 | 攻击者能丢包、延迟、拒绝、重放（都被时间窗、一次性 nonce、设备幂等挡住），但**签不出调用、解不开指令、解不开结果**。它也无法让设备信任任何新身份——信任只在设备配置里 |
| 浏览器被攻破 | 这是新的信任根。XSS 能借你的钥匙签名与解密。私钥被包在不可导出的 AES-GCM 密钥下，只提高取走难度，不改变"同源即等同密钥"这个事实 |
| 设备丢失 | 从控制台移除地址后不再有新调用；但设备本地仍持有历史明文缓存（若有），移除不等于擦除设备 |
| 云端冒充签发者 | 做不到：设备只认配置里那些地址，签名验不过就丢弃 |

## 托管等级

只有一档：**`device`**。密钥只存在于端侧（浏览器 / agent 进程）；云端不持有任何可签名、可解密的材料，只做盲中继。

云端能看到的全部字段：

```
call_id, issuer(签发者地址), device(设备地址), sealed, sig, issued_at, expires_at, 状态
```

看不到：工具名、参数、输出、结果正文。

**代价**：

- 没有装过钥匙的浏览器读不到历史结果，也签不出调用；换设备、清缓存都会遇到。
- 云端无法做任何"内容相关的策略"（比如"禁止 rm -rf"），因为它看不见内容；这类判断只能落在设备本地策略上。
- 恢复材料（passkey 包裹后再存云端，云端仍解不开）尚未实现。

## 云端被攻破时的确切边界

一句话：**泄露的只有设备目录和近期流量记录；没有任何私钥，也不存在"攻破云端就直接控制设备"的路径。**

| 会泄露 | 不会泄露 | 不会发生 |
|---|---|---|
| 已登记地址、在线状态、最近活跃时间、主机名/平台/版本 | 任何私钥（端侧生成，从未上传） | 攻击者伪造指令（签不出） |
| 调用元数据：`call_id`、issuer/device 地址、密文长度、时间、状态 | 指令内容、参数、执行输出 | 攻击者解密任何一条密文 |
| 传输层日志（时间、字节数、状态码） | 设备本地策略 | 攻击者让设备信任新身份（trust 在设备配置里） |

要让这句话**字面成立**，还有两件事必须做，都不是密码学问题：

1. **重放**：攻击者拿到库里一条仍在有效期内的旧调用，可以原样重投。
   对策不是"记住所有 `call_id` 拒绝重复"——重投本身是正常语义（回执丢失时云端会重投）。
   真正要做的是**设备侧内存幂等**：进程内保留 `call_id → 结果` 的映射，
   同一个 `call_id` 再次到达时**不重复执行**，直接回已产出的结果；
   有效期随报文一起签名（`expires_at` 在签名范围内），过期即丢弃。
   进程重启后映射消失——这正是想要的边界：重启后的重投会被有效期与"副作用未知"提示挡住。

2. **控制台来源完整性（部分缓解）**：设备不会被直接控制，但你**登录被攻破的 exe.ntnl.io 时**，
   攻击者的 JS 可以用你浏览器里的私钥签名。控制台现在是 Pages 上的纯静态资源，与中继
   解耦（`VITE_API_BASE` + CORS），但静态资源本身的完整性仍依赖 Pages 的发布流程；
   在拆 origin 完全落地之前，先接受这个风险。

## 谁能拒绝服务

云端的权力没有消失，只是变小了：它可以不投递、投递延迟、丢掉回执、不记录你的设备。
它不能做的事写在上面那张表里。

## 谁在签发

调用由**端侧身份**签发：现在是人的浏览器账户密钥。Agent（跑在任意地方的控制器）同样是一把 Ed25519 身份；
它驱动哪些设备，写在设备的 `trust` 配置里，云端只能存、不能改。

## 不做的事

- 不把任何长期令牌当作执行授权。
- 不在 D1/R2/日志里保留结果明文。
- 不用「服务端签名」代替「账号签名」：云端可以有自己的运维签名，但那不赋予执行权。
