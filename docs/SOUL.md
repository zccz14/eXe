# eXe · Soul

> eXe (Executable) 是 △○✕□ 里的 ✕：可变数的那一个。CTX 改名 Docs 之后，X 让给了执行面。

## 它是什么

一条**只关于「在这台设备上执行，并证明结果」的通道**。设备配置里写下它信任哪些地址，
此后云端可以把调用投递过去，设备验证、执行、封好、回传。

## Statement List

1. **端侧是信任的根。** Cloud 发来的任何调用，在端侧一律先当作不可信输入，直到它通过了设备本地固定的地址验证。不因为"它来自服务端"而放行。
2. **云端不存私钥。** 每一方只有一把 Ed25519 私钥，只在端侧生成、只在那里留存；云端能看到的永远只有公钥（地址）、密文和签名。云端因此签不出调用，也解不开结果——这是产品的地基，不是可调参数。
3. **信任是一个写在设备上的地址列表。** 没有配对、没有确认码、没有批准签名：人把签发者地址写进 `trust`，重启就生效。设备不信任云端的数据库、不信任队列、不信任 worker 的鉴权结果，只信自己磁盘上那份配置。
4. **两个方向都是信封。** 调用封给设备的 X25519 公钥，结果封给签发者的 X25519 公钥，两者都由同一把 Ed25519 密钥派生；云端看到的只有 `call_id`、地址、密文、签名、时间。工具名、参数、输出都不在它手里——这才是"盲中继"。
5. **云端不是安全边界。** 它可以路由、排队、限流、计费，但不能替人签名、不能解密、不能改变一次调用的内容。被完全攻破的 worker 能做的只有丢包、延迟、拒绝服务、重放（会被一次性 nonce 与有效期挡住）。
6. **信任即授权。** 设备只认 `trust` 里那些地址：签名合法就执行，没有第二道本地许可，也没有"这次先确认一下"。代价说清楚——**信任错一个地址，等于把整台机器交出去**（含 `bash`，以设备用户身份、无沙箱）。所以填这个地址必须由人自己做，云端不能代劳。
7. **一次调用只有一份权威记录。** 签名覆盖调用内容、签发者、设备、有效期与密文本身；重放、跨设备、跨账号、过期一律无效。投递是至少一次，执行必须在进程内幂等。
8. **eXe 只做执行面。** 它不是 Agent，不是模型网关，不是聊天界面。它不替你决定做什么，只负责"做了，并给你证据"。
9. **人可以随时切断。** 从控制台移除地址即停止新调用，立刻生效；设备侧 `exe forget` 抹掉本机身份。撤销不会把已有密文变成明文。
10. **没有兼容层。** 这份协议是草稿，改了就改到底：不保留旧字段、旧路径、旧文档。

## 它不应该变成什么

- 不是一个"服务端说跳就跳"的远程管理木马；任何默认信任云端的实现都是错的。
- 不是把结果明文塞进 D1 然后声称"我们内部很安全"。
- 不是在服务端放一把"方便"的私钥来换取功能；需要服务端参与的场景，用一次性的、人授权的委托，而不是长期托管。
- 不是多租户的共享执行池：一台设备只属于一个账号，除非人显式共享。
- 不是只有浏览器能用的东西：设备、CLI、移动端都应该是同一套协议的一等公民。
- 不是为了兼容 Cybion 而把旧的"令牌即权限"模型再带进来。
- 不是需要云端（或任何第三方）替你保管、找回密钥的产品。丢了钥匙就是换身份，重新填地址即可。

## 调用形态（不可破坏的骨架）

```
浏览器生成账号密钥（私钥不出浏览器）→ 只把地址登记到云端
   ↓
人在控制台填设备地址；在设备上填控制台地址（trust）
   ↓
云端排队信封 → SSE 下发 {call_id, issuer, device, sealed, sig, issued_at, expires_at}
   ↓
设备: 验签（issuer 在 trust 里）→ 验时间窗 → 用自己的密钥解开指令 → 执行
   ↓
设备: 用同一把密钥派生的 X25519 封装结果 + Ed25519 签名 → POST 回传
   ↓
云端: 只存信封；浏览器读的时候才解开，读完不落明文
```
